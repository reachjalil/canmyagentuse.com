# Seed Maintenance and Contributor Experience

## Reader Promise

After reading this file, a development team can understand the compatibility decision it covers, audit the supporting evidence, and distinguish a documented surface capability from an unsupported or still-unknown claim.

## Summary

Contributors should edit scoped assertions rather than wide cells. A correction form should preload surface, feature, current evidence, and lifecycle; require an exact source and qualifier; then generate a reviewed data change. Registry imports should be automated but never allowed to overwrite first-party surface facts.

## What We Found

### Contribution workflow

1. Select vendor → product → surface → feature.
2. Choose supported, partial, unsupported, or unknown.
3. Select evidence method and implementation mode.
4. Add environment scope, availability, version, qualifier, and source.
5. Run semantic lint.
6. Open review with generated matrix diff.

### Semantic lint

- unsupported requires explicit negative evidence;
- partial requires a qualifier;
- registry-only claims cannot populate optional methods;
- stale version drift opens a contradiction;
- unknown requires no source and is generated by default;
- a new surface cannot inherit product-wide support without review.

The test backlog should become a fixture repository once the static data workflow is stable.

## Confidence Notes

Normative specifications define requirements but do not prove an implementation. First-party product documentation establishes `documented` support for the named surface and observation date. Official registries establish only the role or portable component they list. No runtime conformance suite was executed in this pass. Missing evidence remains `unknown`, not `unsupported`.
