# Field Notes: living reviews

Owner direction, September 5, 2026: make approachable, review-like explorations of everyday tasks, revisit them as evidence changes, and publish new editions at the same URL. The movie-ticket story is the first example.

## Editorial promise

One practical question, an engaging exploration, a useful verdict. Help someone choose services their agent can actually use. Lead with the outcome and the human handoffs; explain protocols only when they affect the choice. Keep the verdict compact and the evidence available.

Use a concrete opening request, describe the finish line, compare possible outcomes, follow the interesting access constraints, and connect the result to the broader catalog. Keep all prose in portable Markdown under content/news/en. Use ops/templates/field-note.md as the starting point.

## Verdicts

- ready — Ready for this task: a route supports the exact bounded task and prerequisites are explicit. A documentation-based verdict still cannot claim a completed live test.
- conditional — Possible, with conditions: useful routes exist but eligibility, permissions, partner access or other material prerequisites constrain completion.
- handoff — You finish the job: reviewed routes explicitly hand the remaining task to the user.
- unverified — Still exploring: evidence does not establish a useful route or outcome.

The authored headline makes the verdict memorable. The underlying value makes it comparable. There is no star rating, numeric score, or automatic recommendation. A provider must not purchase the verdict, source selection or organic position.

## Evidence and editions

Each review has a stable series number, positive integer version, YYYY-MM-DD review date, verdict, evidence basis, exact first-party source links, what works, the catch and next check. A live-test or mixed label requires published test reports identifying environment, agent, date, authorized scope, human handoffs and read-back outcome. A URL alone does not validate a report; editorial review must read it.

Keep the canonical URL unchanged. Increment the version for a new finding, material correction, new test or substantial editorial revision. Append to history; do not erase earlier history. Before revising, give the previous edition an archiveUrl pointing to its exact full Git commit and Markdown file (or a retained public snapshot). Explain whether the verdict changed and why. Never imply a new test occurred when only presentation changed. Correct mistakes transparently.

HTML, the Markdown twin, /llms-full.txt and /api/v1/reviews.json must agree on the verdict and history. The news index displays the latest edition. Legacy non-review news remains valid.

Do not change the review date or version merely because a scheduled cycle ran. Source changes, new evidence, corrections and meaningful editorial revisions trigger updates. No deadline promises or fake scheduled progress. The existing publishing automation reads PRODUCT-STRATEGY, which points here; use its existing bounded cycle rather than creating another scheduler.

## Next questions (research leads, not support claims)

1. Which note-taking app should I choose for my agent? Compare Notion, Obsidian, OneNote and carefully reviewed additions. Define whether the task is capture, search or editing.
2. Can my agent launch a website from an empty account? Separate signup, account connection, payment, deployment and public URL verification.
3. Can my agent buy a laptop? Compare product discovery, checkout preparation, purchase access and receipt; start with Best Buy and Amazon.
4. Can my agent create a Salesforce org? Distinguish customer signup, scratch orgs and CRM Account records.
5. Can my agent organize my inbox? Define draft versus send, scopes, permissions and confirmation.
6. Can my agent book dinner, a trip or grocery delivery? Research providers and regions before proposing any verdict.

Publish complete, sourced explorations; do not create empty public articles for this backlog. Research cycles still prohibit third-party accounts, outreach, reservations, purchases or software installation. Live tests require separate task-specific authorization.
