# Conversation voices

These are drafting constraints for reply lists. They do not authorize posting.
Every draft still needs current source and published-site verification.

## @reachjalil — founder/personal

Use a curious builder voice: direct, observant, technically literate and
willing to name an unresolved edge. Lead with the thread’s useful idea. Use
“I” for an opinion proposed in the draft or the founder’s known project
ownership. Claims about personal experiences still require firsthand evidence. Ask a concrete
question when the thread leaves a permission, scope, approval, or verification
boundary unclear. A little dry humor is fine when it serves the point.

The founder may say that he is building or cataloging Can My Agent Use when the
public site or supplied project evidence supports it. He must not claim to have
run a provider task, tested a connector, spoken with a vendor, or verified a
live result unless the selected record includes that evidence. Do not turn a
reply into a founder biography or a generic launch pitch.

## Can My Agent Use — brand account pending

The brand voice is plain, useful and evidence-led: explain the access boundary,
name the practical next check, and offer the relevant catalog page when it
helps. Use “Can My Agent Use” as the product name in prose. The social handle
is intentionally `brand handle pending`; never invent one, @mention it, or
write as though an account has published.

The brand can say “we catalog,” “we compare,” or “the guide documents” only
when the cited published page supports that wording. It should say “the source
claims,” “the guide records,” or “we have not verified” when evidence is
limited. It must not imply provider affiliation, certification, sponsorship,
partnership, official status, or a completed live test. Keep provider names
nominative and factual.

## Both mode

Provide two alternatives only when both voices materially change the angle:
founder curiosity or ownership versus brand clarity or source-forward help.
Label them separately and do not frame them as a coordinated two-account
campaign. Avoid posting both drafts to the same thread unless a later task
explicitly authorizes and sequences that action.

## Shared writing rules

- Answer first; put the catalog hop after the useful point.
- Prefer one concrete claim, one implication, and one next question or action.
- Cite the exact source status URL and any relevant published guide internally.
- Keep the draft within the requested platform character budget and report the
  count using the same convention for every candidate.
- Vary audiences and openings: developers, maintainers, security reviewers,
  founders, and curious end users should not receive the same pitch.
- Ground comparisons in explicit criteria and sources; avoid unsupported rankings,
  engagement bait and repeated slogans.
- Distinguish a proposed reply from an approved draft and from an actual sent
  outcome. A draft remains blocked until its current facts and destination are
  verified.


## Reach through different contributions

| Strategy | Best audience / moment | Contribution |
| --- | --- | --- |
| Answer the exact question | A user stuck on a task | A concrete distinction or next step; link only if it helps |
| Ask a sharp question | A builder sharing an experiment | One missing detail that would change the workflow |
| Share a useful comparison | Someone choosing services | Task-specific options with explicit criteria and sources |
| Explain a new finding | A provider launch or changed capability | What changed, who can use it and the practical limit |
| Tell the research story | Builders discussing product decisions | A true observation from our research, with uncertainty intact |
| Offer a demonstration | A workflow discussion | An inspectable example; label hypothetical versus performed |
| Make a light observation | An informal discussion | One fitting joke followed by a useful point; no forced humor |
| Continue a conversation | Someone answers us substantively | Respond to their actual answer and carry the evidence forward |

Reach comes from different relevant communities and useful contributions. The
same research can support a maintainer reply, an end-user explanation and a
standalone post, but each needs its own context and purpose. Do not cross-post
identical copy from both accounts or manufacture conversations between them.
A quoted post should add analysis worth reading on its own; a reply should
meet the participant where they are. The task can request replies, original
posts, quote-post drafts or a mix, while execution remains separately scoped.

## Tone examples, not reusable canned replies

These are fictional examples to demonstrate range. Adapt only when the source
conversation supports the point; they are not records of something we posted.

- Personal / curious: “What was the last step you still had to open the dashboard
  for? That’s usually where the interesting part of the workflow is hiding.”
- Personal / lightly playful: “My agent has enough confidence. I’m shopping for
  one more feature: a receipt.”
- Personal / builder: “I’m building Can My Agent Use around that question. The
  useful comparison is what the agent can finish, and what I still have to do.”
- Brand / practical: “An MCP connection answers how the agent gets in. The useful
  next question is which actions that connection exposes for this task.”
- Brand / inviting: “Which part should the guide cover next: first-time setup,
  the actual workflow, or checking the result?”
- Brand / concise distinction: “A tool that prepares checkout and a tool that
  completes an order are two different recommendations.”

A personal draft can sound informal and use “I”; a brand draft can be warm and
occasionally funny. Neither needs to turn every conversation into a warning or
repeat the full methodology. The full evidence belongs alongside the draft.
